## Overview

Treasury is a self-hosted wealth operating system I built for private use. It combines brokerage investments from Trading 212 and Interactive Brokers with crypto, property, cash, pensions, manually valued assets, liabilities, and cash flows, then normalizes them into one view of net worth, performance, income, and allocation.

I worked across product scope, architecture, broker ingestion, financial services, the read-only MCP surface, and automated verification. The hard part was not drawing charts. It was preserving the meaning of money as data crossed brokers, currencies, storage, derived calculations, and an AI client.

**Documented stage:** private-use system. The AI surface is read-only; scenario tools calculate proposed actions but do not place trades or persist them.

## Three boundaries that define the product

### 01. Integrate source behavior, not just endpoints

The Trading 212 client handles pagination, request pacing, retries, and rate limits, including Retry-After. Interactive Brokers has implemented paths for Client Portal Gateway data, Flex report retrieval and XML parsing, and CSV imports.

The point is not the number of connectors. Each source has different freshness, authentication, pagination, and failure behavior, so ingestion has to preserve source-specific diagnostics instead of pretending every sync is equivalent.

### 02. Reconcile financial meaning before reporting totals

Treasury explicitly prevents broker cash from being counted twice when it appears both as a holding and in an account snapshot. It also avoids subtracting a margin debit twice when the same debt is already represented as negative cash.

Reconciliation checks stored holdings and cash against broker-reported totals and surfaces missing exchange rates, duplicate broker references, missing cost basis, source failures, and stale synchronization. These are accounting semantics expressed as software constraints.

### 03. Give AI a governed view, not database access

The reviewed snapshot defines nine MCP tools for status, portfolio briefings, holdings, instrument detail, income, goals, debt, cash flow, and proposed-action analysis.

The access boundary validates signed JWTs against configured issuer, audience, allowed subject, and project-role claims, and fails closed on verification errors. Tool responses distinguish no data, stale data, partial data, and unavailable sources, and include source-freshness information.

That means an AI client receives both the answer and evidence about whether the underlying inputs are trustworthy enough to interpret.

## Verification

A regression test covers a subtle historical-FX failure: a transaction imported during synchronization must become visible to exchange-rate backfill and be resolved in the same run. The test controls external inputs and checks the stored pipeline result, rather than testing a helper in isolation.

At the reviewed 19 September 2026 snapshot, the successful GitHub Actions run included Ruff, backend pytest tests, Python and JavaScript dependency audits, TypeScript checking, the frontend build, and Playwright. The inspected job log ended with **111 Playwright tests passed**.

That is a dated regression signal, not a claim of 100% coverage or independently audited financial accuracy. Some tests isolate behavior without exercising every live broker path or the complete OAuth journey.

## Outcome

Treasury currently combines multi-asset wealth tracking, brokerage ingestion, financial reconciliation, net-worth and performance views, deterministic scenario analysis, and read-only AI access behind explicit reliability states.

The strongest lesson is domain-specific: in financial software, missing, duplicated, stale, or semantically inconsistent data is not a presentation problem. It is product state that the system has to model.

Treasury remains a private-use product. This case study does not claim trade execution, audited financial accuracy, public adoption, or commercial traction.
